# seungheyon-wiki — 구조 공개판

개인 지식을 축적·갱신하는 LLM 기반 개인 위키의 **설계와 운영 구조**를 공개한 저장소입니다.
실제 데이터(회고·이력서·기업별 기록 등)가 담긴 원본 저장소는 비공개이며, 이곳에는 **스키마 · 스킬 ·
운영 규칙 · 교훈 로그**만 담았습니다.

핵심 아이디어 한 줄: **새 소스가 들어올 때마다 문서를 하나 더 만드는 게 아니라, 이미 있는 문서를 고친다.**

---

## 프로젝트 개요

| | |
|---|---|
| 기간 | 2026.07 ~ 진행 중 |
| 유형 | 개인 작업 환경 |
| 역할 | 지식 구조 설계 · 운영 원칙 수립 · 반복 작업 절차 표준화 |

여러 사이드 프로젝트를 혼자 기획·설계·개발하려면 도구를 잘 쓰는 것만으로 부족했다. AI와 함께
작업할 때마다 맥락이 새로 시작돼 앞선 결정 위에 다음 작업이 쌓이지 않았고, 무엇을 왜 그렇게 정했는지가
대화 안에 흩어져 시간이 지나면 확인할 방법이 없었다. **AI를 더 잘 쓰는 것보다 AI가 매번 같은 기준으로
일하도록 환경을 만드는 쪽이 근본**이라고 보고, 지식 저장 방식과 에이전트 운영 원칙을 직접 설계했다.

세 갈래로 만들었다.

1. **지식 저장 방식을 3계층으로 설계** — Andrej Karpathy가 제안한 LLM Wiki 개념에서 출발해, 자료가
   늘어도 찾는 비용이 함께 늘지 않도록 raw / wiki / schema로 분리. 자료가 쌓일 때마다 처음부터 다시
   찾는 대신 위키 페이지 자체를 갱신하는 방식
2. **반복 작업의 실행 절차를 표준화** — 프로젝트 시작, 이력서 개정 기록, 결정 로그 작성처럼 반복되는
   작업을 스킬로 분리. 지시가 매번 달라져 생기던 결과 편차 제거
3. **시행착오를 운영 원칙으로 승격** — 잘못된 판단을 그때만 고치고 넘어가지 않고, 왜 틀렸는지를 규칙
   문서에 편입한 뒤 작업 시작 시 반드시 읽도록 강제. 같은 실수가 반복되면 규칙 문장을 더 정확하게 고쳐 씀

**결과** — 가족 아카이브 등 다른 프로젝트를 오가며 작업해도 "그때 왜 그렇게 정했는지"를 다시 묻지 않고
이어서 진행할 수 있게 됐다. 이 저장소는 그렇게 만든 문서와 운영 원칙 정의를 그대로 공개한 것이다.

## 왜 만들었나

개인 지식을 LLM에 물려 활용하려 할 때 흔한 접근은 RAG입니다. 문서를 쌓아두고 질의 시점에 검색해서
붙이는 방식입니다. 실제로 운영해 보니 두 가지가 걸렸습니다.

1. **모순이 해소되지 않는다.** 6개월 전 회고와 지금의 판단이 어긋나도, 둘 다 인덱스에 남아 검색 결과에
   같이 딸려 옵니다. 어느 쪽이 현재 버전인지 아무도 결정하지 않습니다.
2. **누적이 아니라 적재다.** 문서가 늘어날수록 검색 품질이 떨어지지, 지식이 정교해지지는 않습니다.

그래서 **검색 대상(raw)** 과 **대표 서술(wiki)** 을 분리하고, 새 근거가 들어오면 대표 서술 자체를
갱신하는 구조로 바꿨습니다. 근거는 계속 쌓이되 결론은 하나로 유지됩니다.

## 3계층 구조

```
├── CLAUDE.md          # 스키마 — 이 위키의 운영 규칙 전체
├── index.md           # 도메인 카탈로그
├── log.md             # append-only 변경 이력 (비공개판에만 존재)
└── <도메인>/
    ├── raw/           # 불변 원본 스냅샷 — LLM은 읽기만 하고 절대 수정하지 않는다
    ├── concepts/      # 합성 페이지 — 계속 갱신되는 "이 사실의 대표 버전"
    ├── people/        # 인물 허브 (해당 도메인에 실제로 필요할 때만)
    └── companies/     # 도메인별 전용 폴더
```

| 계층 | 성격 | 갱신 방식 |
|---|---|---|
| **raw** | 외부에서 온 불변 스냅샷 | 추가만. 수정·삭제 금지 |
| **wiki** | 여러 raw를 종합한 대표 서술 | **덮어쓰기.** 새 근거가 오면 서술 자체를 고침 |
| **schema** | 위 둘을 다루는 규칙 | `CLAUDE.md` — 규칙이 바뀌면 여기부터 |

raw 내부에 같은 사실이 흩어져 있어도 파일을 합치거나 지우지 않습니다. wiki 레이어에 캐논 페이지를
하나 세우고 raw들은 `sources:`로만 링크합니다. 원본 추적성과 단일 결론을 동시에 챙기기 위해서입니다.

## 갱신 판정 — 지지 / 신규 / 충돌

새 근거가 들어오면 기존 서술과 대조해 셋 중 하나로 판정합니다.

- **지지** → 근거만 추가. 서술은 그대로.
- **신규** → 항목 추가.
- **충돌** → 사람에게 확인한 뒤 서술을 고친다.

충돌 판정 기준을 "표현이 다른가"가 아니라 **"기존 서술로 행동을 예측했을 때 새 근거가 그 예측을
빗나가게 하는가"** 로 잡은 것이 실무적으로 가장 중요했습니다. 뉘앙스 차이까지 충돌로 잡으면 매번
사람을 부르게 되고, 구조가 곧 죽습니다.

물어서 정했다면 **그 답변 자체가 새 근거**이므로 raw나 이력에 남깁니다. 판단의 출처가 유실되지
않게 하기 위해서입니다.

## 스킬 레이어

`.claude/skills/` 에 23개 스킬이 있습니다. 스키마가 "무엇을 지킬 것인가"라면 스킬은 "어떤 순서로
할 것인가"입니다.

| 유형 | 스킬 | 역할 |
|---|---|---|
| 코어 워크플로우 | `wiki-ingest` · `wiki-query` · `wiki-lint` | 소스 편입 / 질의 / 건강검진 |
| 자기 모델 | `self-model-ingest` · `daily-feedback` | 성질(trait) 단위 갱신, 누적 모델 기반 피드백 |
| 산출물 | `backend-resume` · `blog-post` · `blog-writer` · `blog-reviewer` · `linkedin-post` | 위키 사실과 대조 후 외부 산출물 생성 |
| 기록 | `decision-journal` · `project-kickoff` · `project-log` | 의사결정·설계 로그 |
| 훈련 | `interview-drill` · `interview-prep` | 질문지 생성·응시·오답 추적 |
| 프로젝트 전용 구현 | `family-archive-*` · `commerce-order-service-rules` · `book-open-interaction` | 특정 저장소의 코드 작업 규칙 |
| 메타 | `skill-creator` · `_shared/` | 스킬 생성기, 공통 규약 |

설계 시 지킨 것 몇 가지:

- **범용 구현 스킬을 미리 만들지 않는다.** 프로젝트마다 스택이 달라 범용화하면 내용이 공허해집니다.
  프로젝트가 실제로 생길 때 `<프로젝트>-<역할>` 접두사로 새로 만듭니다.
- **폴더는 평탄하게.** `.claude/skills/<name>/SKILL.md` 단일 레벨만 인식됩니다. 중첩 폴더는 스킬로
  전혀 잡히지 않는 것을 직접 테스트해 확인했고, 그 결과를 스키마에 못 박아 뒀습니다.
- **검토자는 격리한다.** `blog-reviewer`는 작성자와 같은 컨텍스트에 두면 자기 글을 변호하므로
  별도 서브에이전트로 실행합니다.

## 교훈 로그 (`.claude/LESSONS.md`)

53개 항목이 `- [날짜] 교훈 / 왜 / 적용` 형식으로 쌓여 있습니다. 매 세션 시작 시 읽고 준수하는
것을 규칙으로 강제했습니다. 이 저장소에서 **가장 실질적인 산출물**이라고 보고 있습니다 — 스키마는
설계 의도이고, 교훈 로그는 그 의도가 실제로 어디서 깨졌는지의 기록이기 때문입니다.

예: "근거보다 센 주장을 하지 않는다"는 규칙은 처음부터 있던 게 아니라, 제약을 확인하지 않고
"~때문에 불가능하다"라고 쓴 사례가 반복된 뒤 스키마 §7로 승격된 것입니다.

## 이 저장소에 없는 것

의도적으로 제외했습니다.

- 도메인 데이터 전체 (`career/` · `self-model/` · `projects/raw/` · `blog/`)
- `log.md` — 변경 이력 원본
- `reference/graph.html` — 볼트 전체 파일 목록이 빌드 결과에 포함되므로 제외.
  생성기(`scripts/build-graph.mjs`)와 템플릿은 포함돼 있습니다.

## 저장소 구성

```
├── CLAUDE.md               # 운영 스키마 (핵심 문서)
├── index.md                # 도메인 카탈로그
├── .claude/
│   ├── skills/             # 23개 스킬 정의
│   └── LESSONS.md          # 53개 교훈 로그
├── reference/llm-wiki.md   # 이 위키가 따르는 설계 패턴 원본
├── docs/superpowers/       # 스킬 하네스 설계 문서 (계획 + 스펙)
├── examples/               # 익명화된 샘플 페이지 — 구조가 실제로 어떻게 쓰이는지
└── scripts/
    ├── build-graph.mjs     # 위키링크 그래프 생성기
    ├── notion_*.py         # 노션 → raw 편입 도구
    └── sync_public.py      # 비공개 원본 → 이 저장소 허용목록 동기화
```

## 동기화 방식

`scripts/sync_public.py` 는 **허용 목록(allowlist)** 기반 단방향 복사입니다. 제외 목록 방식이 아닌
이유는, 원본에 새 파일이 생겼을 때 제외 목록은 자동으로 새는 구조이기 때문입니다. 허용하지 않은
경로는 기본적으로 공개되지 않습니다.

```bash
python scripts/sync_public.py --source ../seungheyon-wiki
```

복사 후 익명화 규칙을 적용하고, 민감 패턴이 남아 있으면 **비정상 종료해 커밋을 막습니다.**
