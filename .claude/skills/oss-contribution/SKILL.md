# 오픈소스 기여 스킬

## 목적

실제로 머지되는 OSS 기여를 만든다. 이력서·면접에 쓸 검증 가능한 신호가 목적이다.
속이는 게 아니라 진짜 필요한 수정을 프로젝트 톤에 맞게 낸다. 머지 안 되면 신호는 0이고 평판만 깎인다.

## 절대 규칙

1. **진짜 기여만.** 실재하는 버그·문서 공백·테스트 부족을 고친다. 스팸·양산 금지.
2. **AI 티 제거(사람 문체).** 과한 불릿·이모지·"Certainly"·장황한 서론·em-dash(—) 전면 금지. 대상 프로젝트의 기존 커밋·PR 톤을 따라간다.
3. **본인이 이해.** 면접에서 "이거 설명해봐"가 나온다. 코드를 이해하고 방어할 수 있어야 제출한다.
4. **검토 게이트.** 브랜치 push·PR 오픈 전에는 반드시 사람(나) 승인을 받는다. AI가 알아서 실제 PR을 올리게 두지 않는다.
5. **서두르지 않는다.** 이슈가 모호하면 먼저 질문하고, 명확하면 바로 PR 한다. PR 올린 뒤 리뷰가 안 붙어도 2~3주는 정상이다.

## 절차

### 1. 탐색

mergeable `/oss` 게시판(접근 코드는 멘토에게 문의)에서 미점유(연결된 열린 PR이 없는) 이슈를 먼저 본다. 없으면 관심 있는 저장소에서 `good first issue`/`help wanted` 라벨로 직접 검색한다(`gh issue list --repo <owner>/<repo> --label "good first issue,help wanted"`).

### 2. 개별 검증 (가장 중요한 단계)

**라벨이 붙어있고 mergeable에 "미점유"로 보여도, 실제로는 이미 점유된 경우가 훨씬 많다.** 아래를 전부 확인하기 전엔 착수하지 않는다.

- **할당자(assignee) 확인.** 있으면 스킵.
- **코멘트를 끝까지 읽는다.** "제가 할게요" 코멘트가 최근(2~3주 이내)에 있으면 스킵한다. 오래됐으면(1~2개월 이상) `gh search prs --repo <owner>/<repo> --author <그 사람>`으로 실제 PR을 냈는지 확인한다. PR이 없으면 진짜 비어있는 것.
- **이미 해결됐는지 확인.** 코멘트 중에 "이거 다른 PR로 이미 됐어요" 같은 말이 있는지 꼭 확인한다.
- **설계 논쟁이 진행 중인지 확인.** 메인테이너와 여러 사람이 몇 년째 접근 방식을 논쟁 중이면(예: "이걸 어떻게 구현할지 아직 못 정했다") 피한다. 코드 몇 줄 고치는 문제가 아니라 합의가 안 된 문제다.
- **이슈 본문만 믿지 않는다.** 실제 코드를 열어서 지금도 그 문제가 있는지 직접 확인한다. 이슈가 오래됐으면(1년 이상) 그 사이 코드가 리팩터링돼서 스코프가 달라졌을 수 있다. 관련 원본 PR이 있으면(`git log -S "관련키워드"`) 찾아서 실제로 무엇을 건드렸는지 본다.

### 3. 기여

fork → 브랜치 → 패치 → 테스트 통과 확인 → 커밋(프로젝트 컨벤션대로) → **여기서 나에게 보여주고 승인받기** → 승인 후 `gh pr create`.

PR 제목·본문·커밋 메시지는 담백하게. 문제 → 무엇을 고쳤는지 → (필요하면) 어떻게 검증했는지 순서로 짧게 쓴다.
