# commerce-order-service-rules

이커머스 주문 서비스 전용 작업 규칙. **구현·문서를 막론하고 이 저장소에 관련된 모든 작업에 적용된다.**
다른 프로젝트에는 재사용하지 않는다.

## 왜 이 규칙이 존재하는가

이 프로젝트는 멘토(`<mentor>`)가 실제 채용 과제 전형과 동일한 방식으로 리뷰하는 과제다.
멘토가 작업 시작 시점에 다음을 못박았다.

> AI가 작성한 문서, 코드 모두 다 네가 책임질 수 있어야 된다.
> "AI가 이렇게 한 거다, 이건 내 생각 아니다" ← 절대 안 됨.
> 작성은 AI 시키되 철저히 네가 모든 걸 책임질 수 있는 수준까지 검토해야 한다.
> 핵심: PR에서 내가 코드 리뷰했는데 위 반응 나오면 절대 안 됨.

즉 이 프로젝트에서 산출물의 품질 기준은 "그럴듯한가"가 아니라 **"사용자가 리뷰에서 자기 말로 방어할 수 있는가"** 다.
AI가 공백을 매끄럽게 메울수록 사용자가 설명할 수 없는 문장이 늘어나므로, **매끄러움이 오히려 실패**다.

## 규칙

**1. 설계 공백은 채우지 않고 멈춘다**
지시받지 않은 결정이 필요해지면 임의로 정하지 않고 묻는다. **"합리적인 기본값"도 결정이므로 예외가 아니다.**

**2. 문서의 모든 주장에는 출처가 있어야 한다**
셋 중 하나여야 한다 — (a) 요구사항 명세 (b) 사용자가 직접 말한 것 (c) 사용자가 검토하고 승인한 것.
셋 다 아니면 쓰지 않는다.

**3. 추론은 문서에 넣기 전에 분리해서 승인받는다**
AI가 이어붙인 논리는 초안에 바로 반영하지 않고 "이건 추론입니다"로 먼저 제시한다.

**4. 요구되지 않은 것은 만들지 않는다**
명세에도 없고 지시도 없는 모듈·필드·추상화·구조를 관례로 추가하지 않는다.

**5. ADR은 사용자가 자기 말로 설명할 수 있는 근거만 담는다**
근거의 밀도보다 **방어 가능성**이 우선이다. 문장이 그럴듯한 것보다 사용자가 리뷰에서 설명할 수 있는 것이 중요하다.

**6. 산출물을 낼 때 "내가 채운 공백" 목록을 함께 낸다**
매번 무엇을 임의로 판단했는지 명시적으로 나열한다. 없으면 "없음"이라고 적는다.
이것이 1~5번이 지켜졌는지 확인하는 장치다.

**7. 커밋·PR 전 자문**
*"이 변경의 모든 줄을 사용자가 코드 리뷰에서 자기 것으로 방어할 수 있는가?"* 아니면 올리지 않는다.

**8. 테스트는 사용자가 설계하고, 코드 작성은 AI 가 해도 된다**

명세 원문(협업 규칙 "AI 활용과 TDD")은 *"AI 에게 테스트 코드 작성을 맡기지 않는다"* 이지만,
**2026-08-22 멘토 1:1 에서 구두로 완화되었다.** 실제 적용 규칙은 다음과 같다.

- **사용자가 직접 설계하는 것 (AI 가 대신하지 않는다)**
  1. **테스트 단위** — 어디까지 실제 객체를 쓰고 어디부터 목/페이크로 대체할지(클래시스트 경계)
  2. **테스트 케이스** — 무엇을, 어떤 상태로 검증할지
- **AI 가 해도 되는 것** — 위 설계를 코드로 옮기는 작업
- **설계를 받지 않은 상태에서 AI 가 테스트 케이스를 스스로 만들어내지 않는다.** 규칙 1(설계 공백을
  채우지 않는다)의 특수한 경우다. 케이스가 부족해 보이면 추가로 만들지 말고 사용자에게 묻는다.

평가 기준 4번이 **"테스트 코드를 본인이 직접 설계·작성했는가, 상태 기반으로 의미 있는 검증을 하는가
(가장 꼼꼼히 본다)"** 이므로, 완화된 것은 *작성*이지 *설계*가 아니다.

**명세 원문과 다르므로**, 이 완화 사항은 근거(구두 확정, 2026-08-22)와 함께 저장소 문서에 남긴다.
남기지 않으면 리뷰어에게는 협업 규칙 위반으로 보인다(평가 기준 5번).

**9. `@Transactional` 은 세어 보고 붙인다 (기계적 판정)**

관례로 붙이다 리뷰에서 세 번 지적받았다. 생각으로 판단하지 말고 다음 순서를 그대로 따른다.

1. 메서드 본문에서 **저장소 호출 횟수를 센다.**
2. **1회면 붙이지 않는다.** JPA 저장소 메서드 하나가 이미 자기 트랜잭션을 연다. 조회 전용도 마찬가지다.
3. **2회 이상이면 붙인다.** 그 둘이 한 묶음으로 성공·실패해야 하는 것이 맞는지 한 줄로 근거를 남긴다.
4. **예외는 두 가지뿐이다** — (a) 커밋 후 이벤트를 발행해야 해서 발행 시점에 트랜잭션이 열려 있어야 할 때,
   (b) 커밋 후 리스너 안에서 저장할 때(`REQUIRES_NEW` 가 필요하다. `REQUIRED` 는 끝나가는 트랜잭션에
   합류해 저장이 유실된다). 이 두 경우는 근거를 주석으로 남긴다.
5. 붙였다면 **무조건 "내가 채운 공백" 목록에 올린다**(규칙 6). 근거가 위 3·4번 중 하나로 지목되지 않으면 뗀다.

PR 직전에 `grep -rn "@Transactional" modules/*/src/main` 으로 전수 대조한다.

규칙이 추상적으로 읽히지 않도록 기록해 둔다. 둘 다 사용자가 직접 잡아냈다.

| 사례 | 어긴 규칙 | 무슨 일이 있었나 |
|---|---|---|
| 아키텍처 문서 3.5절 "그래서 관계는 Conformist 다" | 3 | 사용자의 수기 원본에 없던 추론을 문서에 먼저 써넣고 나중에 확인을 구했다. 순서가 반대였다. 사용자가 "불필요한 항목"이라며 삭제 지시. |

## 순서

1. **명세를 먼저 읽는다.** 기억에 의존하지 않는다. 해당 마일스톤의 요구사항·검증 방법·완료 조건을 그대로 확인한다.
2. **위키 허브 페이지를 읽어** 그 사이 결정이 바뀌지 않았는지 확인한다.
3. **작업 전에 공백을 먼저 식별한다.** 지금 만들 산출물이 무엇을 입력으로 삼는지 나열하고, 손에 없는 것이 있으면 그것부터 요청한다.
4. **작업한다.** cwd·git 안전수칙은 `.claude/skills/_shared/implementation-conventions.md` 참고.
5. **산출물과 함께 "내가 채운 공백" 목록을 낸다** (규칙 6).
6. **커밋·푸시는 매 작업 단위 종료 시 사용자 확인을 받는다** (위키의 자동 커밋 규칙이 이 저장소로 확장되지 않는다).

## 명세가 정한 협업 제약 (요약 — 원본은 명세 5번)

- Private 저장소 / `main` 직접 푸시 금지 / 마일스톤·기능 단위 브랜치 + PR
- Conventional Commits, 한 커밋은 하나의 관심사
- **PR 하나에 커밋 최대 3개, 추가 코드 500줄 미만**(테스트 코드 제외)
- PR 설명에 무엇을·왜 바꿨는지와 검증 방법, 그리고 검증 증빙을 포함
- 각 마일스톤은 검증 시나리오 통과 + 증빙 첨부 + **코드 오너 승인**을 모두 충족해야 완료

## 평가 기준 (명세 6번 — 5개 전부)

1. 왜 그렇게 설계했는지 설명할 수 있는가 (트레이드오프 인식)
2. 각 문제(오버셀, 중복 결제 등)를 실제로 재현하고, 해결됐음을 상태 검증과 데이터로 증명했는가
3. 실험·측정 결과를 근거로 의사결정했는가, 아니면 추측으로 넘어갔는가
4. **테스트 코드를 본인이 직접 설계·작성했는가, 상태 기반으로 의미 있는 검증을 하는가 — 「가장 꼼꼼히 본다」**
5. 커밋·PR·문서가 협업 규칙을 따르고 있는가
