# 구현 스킬 공통 규약

각 프로젝트 전용 구현 스킬(예: `family-archive-designer`/`family-archive-developer`/`family-archive-devops`)이
공유하는 안전수칙. 이 스킬들은 `seungheyon-wiki` 세션에서 실행되지만 실제 코드는 **별도 저장소**(프로젝트 허브
페이지의 "구현 저장소" 참고)를 대상으로 한다. wiki는 컨텍스트·설계·의사결정 축적소, 코드 저장소는 산출물만
담는다는 역할 분담을 유지한다.

## 대상 프로젝트/저장소 찾기
1. 어느 프로젝트인지 확인 (모호하면 AskUserQuestion).
2. `projects/concepts/프로젝트_<이름>.md`를 읽어 MVP 요구사항·기술 스택·"구현 저장소" 경로를 확인한다.
   "구현 저장소" 섹션이 없으면 사용자에게 물어보고 허브 페이지에 추가한다.
3. 관련 결정(`projects/concepts/decisions/`)도 필요한 만큼 읽어 기술적 근거를 확인한다.

## 작업 디렉터리 안전수칙 (2026-07-29 직접 테스트로 확인된 사실 — 추측 아님)

이 세션의 "기본 작업 디렉터리(primary working directory)"는 `seungheyon-wiki`다. 이 디렉터리를 벗어나는 `cd`와
벗어나지 않는 `cd`의 동작이 서로 다르다는 것을 실제로 확인했다:

- **기본 작업 디렉터리 바깥(예: `family-archive`, 형제 폴더)으로 단독 `cd`한 경우**: 그 호출 안에서 즉시
  "Shell cwd was reset to `<기본 작업 디렉터리>`"라는 메시지와 함께 **cwd가 자동으로 원상복구된다.** 즉 이후
  호출에서 `family-archive`에 남아있는 것을 기대할 수 없다 — 항상 리셋된다.
- **기본 작업 디렉터리 안쪽(예: `projects/concepts`, 하위 폴더)으로 단독 `cd`한 경우**: 리셋되지 않고 **다음
  호출까지 그대로 유지된다.** (실제로 `projects/concepts`에 머문 채 다음 호출에서 그래프 빌드 스크립트를
  실행했다가 엉뚱한 경로에서 실패한 사례가 있었다 — 이 폴더 안쪽 persist 동작 때문.)

**결론**: `family-archive`(기본 작업 디렉터리 바깥)에서 명령을 실행할 때는 단독 `cd`가 애초에 안 먹히므로,
**반드시 한 Bash 호출 안에서 `cd <구현저장소 절대경로> && <명령>`처럼 체이닝**해야 명령이 그 경로에서 실행된다.
반대로 wiki 내부 하위 폴더는 cd가 실제로 유지되므로, 그 상태에서 무심코 다른 폴더 기준 스크립트(예: 저장소
루트 기준 상대경로를 쓰는 `node scripts/*.mjs`)를 돌리면 실패할 수 있다 — 어느 쪽이든 파일 경로는 가능하면
절대경로로 명시하고, 명령 직전에 `pwd`로 확인하는 습관이 안전하다.

## git 정책 (저장소별로 다름 — 절대 혼동하지 않는다)
- **seungheyon-wiki**: 파일을 변경한 턴마다 자동으로 add·commit·push (기존 승인, `[[feedback_auto_commit_push]]` 참고).
- **구현 저장소(family-archive 등)**: 자동 커밋·푸시 **하지 않는다**. 작업 단위가 끝날 때마다 사용자에게 확인받은 뒤
  진행한다 — 이 승인은 저장소마다 별도이며, wiki의 자동 승인이 다른 저장소로 확장되지 않는다(2026-07-29 확인됨).

## 비밀정보 취급
- API 키·DB URL·비밀번호 등 자격증명은 **절대 wiki에 기록하지 않는다** (frontmatter, 본문, 커밋 메시지 모두 포함).
  실제 값은 구현 저장소의 `.env`(gitignore 대상) 또는 각 플랫폼(Cloudflare/Supabase) 대시보드에만 둔다.
  wiki에는 "어떤 값이 어디에 등록되어 있다"는 사실만 남긴다(값 자체는 남기지 않음).

## 새로운 설계 결정이 나오면
구현 도중 요구사항 해석이 갈리거나 기술적 결정이 새로 필요해지면, 코드부터 짜지 말고 먼저 `project-log`로
wiki에 결정을 남긴 뒤 그 결정에 따라 구현한다(설계는 wiki, 실행은 코드라는 역할 분담 유지).

## 완료
- 구현 저장소 변경사항은 위 git 정책대로 사용자 확인 후 커밋·푸시.
- wiki 쪽에서 파일을 바꿨다면(허브 페이지의 "구현 저장소" 섹션 신설 등) 규칙 #1에 따라 자동 커밋·푸시.
