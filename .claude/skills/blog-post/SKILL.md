# blog-post

블로그 포스팅 전체 워크플로우를 오케스트레이션한다.
학습 내용을 입력받아 초안 작성 → 리뷰 → 사용자 전달까지 진행한다.

---

## 언제
- 트리거: "블로그 글 써줘", "이 소스로 블로그 초안 만들어줘", "블로그 포스트 작성".

---

## 실행 흐름

### 1. 사전 확인

`blog/concepts/스타일_프로필.md` 파일이 존재하는지 확인한다.

존재하지 않으면 다음을 안내하고 중단한다.
> "스타일 프로필이 없습니다. 먼저 blog-extract-style을 실행해 문체를 학습시켜 주세요." ([[blog-extract-style]])

---

### 2. 초안 작성 (1차)

`Skill` 툴로 [[blog-writer]] 스킬을 실행한다.

- 학습 내용 수집, Q&A, 초안 작성이 모두 이 단계에서 이루어진다.
- 작성이 완료되면 초안 전문과 수집된 원본 자료(학습 내용 + Q&A 답변 전문)를 보관한다. 이후 단계에서 계속 참조한다.

---

### 3. 리뷰 (1차)

`Agent` 툴로 [[blog-reviewer]]를 격리 세션에서 실행한다.

Agent 호출 시 프롬프트에 아래 내용을 포함한다.

```
.claude/skills/blog-reviewer/SKILL.md 스킬의 지침을 읽고 따라 아래 초안을 리뷰하라.
스타일 프로필은 blog/concepts/스타일_프로필.md 에서 직접 읽어라.

---

**초안**
[초안 전문]

---

**원본 자료 (학습 내용 + Q&A 답변)**
[원본 자료 전문]
```

**프롬프트에 검증 항목을 임의로 좁혀 적지 않는다.** 호출자가 지정한 항목만 보게 되어 스킬이 정한 적대적 검사(HB-1)가 사실상 비활성화된다. 이전 회차의 지적 사항은 "이번에 이렇게 고쳤으니 재발 여부를 확인하라"는 **추가** 정보로만 전달하고, 스킬 본래의 검사 범위를 대체하지 않는다.

리뷰 결과를 수신하고 종합 판정을 확인한다.

- **통과** → [5단계: 사용자 전달]로 이동
- **재작성 요청** → [4단계: 재작성 루프]로 이동

---

### 4. 재작성 및 재리뷰 루프 (최대 2회 — 리뷰는 총 3차까지)

아래 4-1 → 4-2를 **최대 2회 반복**한다. 각 회차는 다음과 같이 진행한다.

#### 4-1. 재작성

`Skill` 툴로 [[blog-writer]] 스킬을 재작성 모드로 실행한다.

`blog-writer` 호출 시 아래 내용을 전달한다.
- 직전 초안 전문
- 원본 자료 전문
- 직전 리뷰 결과 전문 (수정 우선순위 포함)
- **이전 회차들에서 이미 지적돼 고친 항목 목록** (같은 곳을 되돌리지 않게 하기 위함)

재작성된 초안을 보관한다.

#### 4-2. 재리뷰

3단계와 동일한 방식으로 `Agent` 툴로 [[blog-reviewer]]를 실행한다.
재작성된 초안과 원본 자료를 전달한다.

- **통과** → [5단계: 사용자 전달]로 이동
- **재작성 요청** → 반복 횟수가 남아 있으면 4-1로 돌아가고, **3차 리뷰까지 마쳤으면 결과와 관계없이 [5단계: 사용자 전달]로 이동한다.**

#### 4-3. 루프 운영 규칙

- **같은 지적이 2회 연속 반복되면 그 항목은 자동 수정을 멈추고 사용자에게 판단을 넘긴다.** 라이터와 리뷰어의 판단이 엇갈리는 지점일 수 있으므로, 계속 고치면 오히려 품질이 떨어진다. 5단계 전달 시 "리뷰어와 라이터가 합의하지 못한 항목"으로 따로 보고한다.
- 리뷰어의 지적이 **틀렸다고 판단되면 그대로 반영하지 않는다.** 근거를 확인해 반박 가능하면 수정하지 않고, 그 사실을 5단계 보고에 남긴다. 리뷰어도 오지적을 할 수 있다.
- 리뷰어의 `미검증 의심` 항목은 자동 수정 대상이 아니다. **5단계에서 사용자에게 그대로 전달**해 확인을 받는다.

---

### 5. 사용자 전달

저장 전에 파일명에 제목을 반영할지 먼저 묻는다.

> "초안 파일명에 제목을 반영할까요? 반영한다면 어떤 제목으로 할까요? (원치 않으면 기존처럼 날짜만 사용합니다)"

- **제목을 받은 경우**: `blog/drafts/YYYY-MM-DD_<제목>.md`로 저장한다. 제목의 공백은 밑줄(`_`)로 바꾸고, 파일명에 쓸 수 없는 특수문자(`? : \ / * < > | "`)는 제거한다.
- **원치 않는다고 답한 경우**: 기존대로 `blog/drafts/YYYY-MM-DD_draft.md`로 저장한다.
- 같은 날짜·같은 이름으로 이미 파일이 있으면 `_2`, `_3`... 넘버링한다.

저장 후 아래 형식으로 사용자에게 전달한다.

```
---
[최종 초안 전문 — 마크다운 형식]
---

**리뷰 결과 요약**
- 저장 경로: blog/drafts/YYYY-MM-DD_draft.md
- 리뷰 횟수: N차 (최대 3차)
- 최종 판정: 통과 / 미통과
- 항목별 최종 점수: S-1: X/5 / S-2: X/5 / S-3: X/5 / S-4: X/5 / S-5: X/5 / S-6: X/5
```

(최종 판정이 미통과인 경우에만 추가)
```
**미통과 항목 및 리뷰어 피드백**
[해당 항목의 리뷰어 피드백 원문]
```

아래 세 가지는 **판정과 무관하게 남아 있으면 반드시 함께 전달한다.** 자동으로 처리하고 넘어가서는 안 되는, 사용자 확인이 필요한 항목들이다.

```
**사용자 확인이 필요한 항목**
- 미검증 의심: [리뷰어가 확정하지 못한 의심 + 무엇을 확인하면 판정 가능한지]
- 빠진 전제·대안: [HB-1의 (b)-4 지적. 무엇을 다룰지는 필자 판단이므로 반영하지 않고 넘김]
- 합의하지 못한 항목: [같은 지적이 2회 연속 반복돼 자동 수정을 멈춘 것, 또는 리뷰어 지적이 틀렸다고 판단해 반영하지 않은 것과 그 근거]
```

전달 후 다음을 안내한다.
> "위 내용은 초안입니다. 이대로 사용하셔도 되고, 수정이 필요한 부분을 말씀해 주시면 반영하겠습니다."

---

### 6. 티스토리 발행

*(보류 — Tstory 발행 MCP는 아직 연결돼 있지 않다. MCP가 구현되면 이 단계에 발행 확인 질문 → `publish_post` MCP 호출 → 결과 URL 전달 로직을 채운다.)*

지금은 사용자에게 다음을 안내하고 종료한다.
> "발행 자동화는 아직 준비 중입니다. 위 초안을 복사해서 Tstory에 직접 붙여넣어 발행해 주세요."
