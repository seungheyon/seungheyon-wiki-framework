## 2026-07-29 — 문장 단위 정밀 수정 후 즉시 발행

**상황**: "코드리뷰를 하는 이유" 블로그 글(https://shnowball.tistory.com/216) 홍보 포스트, 정의형 훅 버전.

**사용자 승인 방식**: 문장 번호를 매겨 각 문장의 어미/표현을 개별 지정("2번째 문장 A → B" 식)하고, 판단이 필요한 지점(추상적 관점을 담은 문장, 마무리 문장)에는 "더 나은 제안 있으면 해줘, 없으면 바로 발행해줘"로 승인 범위를 스스로 좁혀줬다.

**적용한 패턴**:
- 어미 다양화: "-거든요"/"-더군요" 계열로 몰리지 않게 "-습니다"/"-어요" 평서형을 섞어 과하게 구어체로 쏠리는 것을 방지.
- 단어 선택: "진짜 이유는" → "진짜 의미는" — 코드리뷰의 목적을 재해석하는 문맥에는 "이유"보다 "의미"가 더 맞음.
- 마무리 문장: "전체 내용은 여기 정리했습니다"(보고형) → "대화를 복기하며 정리한 생각을 글로 남겼습니다"(회고형) — 링크드인 훅 포스트에도 리포트형보다 개인적 회고 톤이 낫다는 신호.
- 판단이 필요한 문장(예: 코드와 문서의 동기화 성격 차이를 설명하는 추상적 문장)에는 에이전트가 더 간결한 대안을 먼저 제시하고, 사용자가 별도 반박 없이 진행 지시를 유지하면 그 대안으로 확정한 뒤 곧바로 발행 — 왕복을 최소화.

**시사점**: 사용자가 승인 범위를 문장 단위로 명확히 좁혀주면, 에이전트는 "대안 제시 → 확정 → 발행"을 한 턴 안에 끝낼 수 있다. 판단이 필요한 지점만 골라 대안을 제시하고, 나머지는 지정된 문구를 그대로 신뢰해서 반영하는 게 발행 마찰을 줄인다.

## 2026-08-01 — 같은 소재로 규칙 개정 후 재발행, 2회 미세수정으로 즉시 승인

**상황**: 같은 "코드리뷰를 하는 이유" 글로 재발행. 이번엔 스킬 규칙이 여러 번 개정된 뒤(인용구 압축 허용+어투 보존, 대명사 격식 통일, 짧은 문장 톤)라 3버전 자체의 품질이 처음부터 높았다.

**사용자 승인 방식**: 1번 초안에 두 군데만 정확히 지정해서 수정 요청("어긋날 씨앗을 품습니다 → 품고 있습니다", 마지막 문단 어순 조정) → 반영된 결과를 다시 보여주지 않고 "바로 발행까지 가자"로 최종 승인까지 한 번에 지시.

**적용한 패턴**:
- 부끄럽다는 감정을 직접 명시("부끄럽지만")하는 자기 노출형 표현을 사용자가 직접 원해서 삽입 — 에이전트가 먼저 제안한 담백한 사실 진술("팀 프로젝트에서 제가 가장 지루해했던 일이...")보다 감정어를 더한 버전을 사용자가 선호. 톤 규칙의 "과장된 감정 서술 금지"는 AI가 임의로 지어내는 감정에 대한 것이지, 사용자가 명시적으로 원하는 자기 서술까지 막는 게 아니라는 걸 확인.
- "~씨앗을 품습니다"(단정) → "~씨앗을 품고 있습니다"(지속상) — 짧은 문장 기조 안에서도 동사 상(相) 하나로 어감이 달라짐. 짧게 쓰라는 지시가 항상 더 짧은 어미를 뜻하는 게 아니다.
- 마지막 문단은 쉼표 위치와 어순만 바뀌었는데("A가 아니라 B를 묻습니다" → "이제 리뷰할 때, A가 아니라 B를 묻습니다") 문장의 리듬이 확 달라짐 — 사용자가 최종 마무리 문장에 특히 민감하게 손을 대는 경향.
- 두 지점 수정 후 별도 재확인 절차 없이 "바로 발행까지 가자"는 한 문장으로 4단계(확인)와 5단계(발행) 승인을 동시에 처리 — 수정 지시 자체가 이미 승인 의사를 포함한 경우로 판단해도 됨.

## 2026-08-01 — 인과관계(계기) 순서 오류 수정, 문장 단위 재수정 후 발행

**상황**: "CI의 사실과 오해" 글(https://shnowball.tistory.com/218, 이미 raw로 편입돼 있던 `CI의_사실과_오해_260731.md`를 원문으로 사용) 홍보 포스트, 질문형 훅.

**사용자 승인 방식**: 1차 초안에서 사건의 인과관계 순서 자체가 틀렸다는 걸 사용자가 지적("나는 내 지난 글을 보고 파울러 아티클을 읽은 게 아니라, 파울러 아티클을 읽으며 지난 글의 오해를 되돌아본 것") → 전체를 그 순서로 다시 쓴 뒤, 이어서 문장 2곳 지정 수정("~떠올랐습니다" → "~떠올라서 '그땐 어떻게 정리해 뒀나' 하고 다시 찾아봤습니다", "~이었습니다" → "~이었어요") + 마무리 직전 "전문은 여기 있습니다." 삭제 → "응 좋다, 이대로 발행해줘"로 최종 승인.

**적용한 패턴**:
- **원문에 없는 인과관계를 함부로 재구성하지 않는다.** 원문 텍스트만으로는 "지난 글 재검토 → 파울러 아티클 열람"과 "파울러 아티클 열람 → 지난 글 재검토" 두 순서 모두 그럴듯하게 읽혔는데, 실제 순서는 후자였다. 원문에 계기 순서가 명시적으로 드러나지 않으면 에이전트가 임의로 자연스러운 쪽을 골라 서술하지 말고, 애매하면 사용자에게 확인하거나 원문 문장 순서를 그대로 따르는 게 더 안전하다.
- "-이었습니다"(격식체) → "-이었어요"(반격식체, 여전히 존댓말이지만 더 부드러움) 로의 미세 조정 — 문장 하나에만 부분적으로 격식을 낮추는 것도 허용된다. 문단 전체 톤을 통일해야 한다는 규칙이 문장 단위 뉘앙스 조정까지 막는 건 아니다.
- 클릭 유도용 관용구("전문은 여기 있습니다")를 명시적으로 빼고 링크만 남기는 선택 — 마지막 인사이트 요약 문장 자체가 이미 글을 마무리짓기 때문에, 링크로 넘어가는 연결 문구가 없어도 어색하지 않다.

## 2026-08-03 — 발행 직후 사용자가 "잘렸다" 신고, 원인 규명 후 삭제·재발행

**상황**: 위 CI 글 발행 직후 사용자가 "깨진 빌드는 즉시 수정하기"에서 게시글이 끊기고 이후 내용이 없다고 보고.

**원인 진단 과정**:
- 로컬 파일(`post_text_ci.txt`, `body_ci.json`)은 끝까지 완전한 내용을 담고 있어 우리 쪽 전송은 정상이었음을 먼저 확인.
- `GET /rest/posts/{urn}`으로 실제 저장본을 조회하려 했으나 403(`ACCESS_DENIED`) — 우리 앱(`w_member_social`만 보유)은 조회 권한이 없다는 것도 함께 확인.
- WebSearch로 LinkedIn `commentary` 필드가 "little text format" 마크업을 쓰며, 예약 문자(`\ | { } @ [ ] ( ) < > # * _ ~`)를 이스케이프하지 않으면 **그 문자부터 뒤 전체가 에러 없이 잘려서 발행된다**는 걸 확인 — 실제 잘린 지점이 텍스트의 첫 미이스케이프 괄호와 정확히 일치.
- `PATCH`(PARTIAL_UPDATE)로 수정도 시도했으나 404 — 수정 권한도 없어 삭제 후 재발행만 가능하다는 결론.

**사용자 처리**: 게시글을 본인이 직접 삭제. 재발행 시 "괄호 부분은 발행 버그와 무관하게 내용상 마음에 안 들었다"며 통째로 삭제 요청 — 버그 수정과 콘텐츠 편집 요청이 같은 지점에서 겹친 사례.

**적용한 패턴**:
- 발행 실패는 HTTP 상태 코드로만 판단하면 안 된다. 이번 건은 **201 Created(성공)를 반환했는데도 내용이 잘린** 경우라, 상태 코드 확인만으로는 절대 못 잡는다. 발행 후 사용자의 실제 화면 확인이 유일한 검증 수단(우리 앱은 조회 권한도 없음).
- 재발 방지는 사후 확인이 아니라 **발행 직전 전처리(이스케이프)**로 근본 차단하는 쪽으로 스킬을 고쳤다 — `SKILL.md` 5단계 참고.

## 2026-08-04 — 초안 품질 교정: 스킬 산출물 vs 사용자가 실제 원한 방향

**상황**: DDD 글(shnowball.tistory.com/219) 포스트. 재발산을 3회 거친 뒤에도 사용자가 문장 단위로 교정을 요청했다. 이 항목은 **스킬이 만들어낸 문장**과 **사용자가 실제로 원한 문장**을 나란히 두어, 다음 실행 때 처음부터 후자 쪽으로 쓰기 위한 참고 자료다.

### 교정 1. 독자가 모르는 것을 아는 척 쓰지 않는다 (가장 중요)

- **스킬 산출물**: 근본 원인(도메인 전문성 부재) 서술 직후 곧바로 *"여기서 두 번째 문제가 생겼습니다. 이 판단을 팀에 어떻게 전달하느냐였습니다."*
- **문제**: 포스트 어디에도 "어떤 판단"인지 쓰여 있지 않다. 원문 블로그에는 그 판단(전면 도입을 접고 최소 범위로 줄인다)이 명시돼 있어서 **에이전트는 알고 있지만 독자는 모른다.** 원문을 읽고 요약하다 보면 원문 지식이 새어 들어와, 포스트 단독으로는 성립하지 않는 문장이 나온다.
- **사용자가 원한 형태**: 지시대명사가 가리키는 대상을 **포스트 안에서 먼저 진술**한다. 수정 후에는 앞에 *"그래서 전면 도입을 멈추고 적용 범위를 최소한으로 줄여야 한다고 판단했습니다."* 를 넣어 해결.
- **일반 규칙**: 초안 완성 후, **원문을 안 읽은 사람이 이 포스트만 읽는다고 가정하고** 모든 지시어("이 판단", "그 문제", "앞서 말한", "이런 상황")가 포스트 내부에 선행 서술을 갖는지 점검한다. 없으면 선행 문장을 만들거나 지시어를 풀어 쓴다.

### 교정 2. 자기 과시로 읽히는 서술을 피한다

- **스킬 산출물**: *"옳은 말이라도 지금 하고 있는 작업을 정면으로 부정하면, 사람은 자기 논리를 방어하는 쪽으로 움직입니다."*
- **문제**: 사용자 표현으로 "자아비대한 느낌". 자신의 의사소통 능력·통찰을 과시하는 톤으로 읽힌다. 원문 블로그에는 실제로 있는 서술이지만, 짧고 외부 노출되는 링크드인 포스트에서는 무게가 달라진다.
- **사용자가 원한 형태**: *"따라서 이 이야기를 꺼내면 어떤 식으로든 반대 의견에 부딪힐 거라 생각했습니다."* — 인간 심리에 대한 일반론을 선언하는 대신, 본인이 그때 한 예상만 담담히 진술.
- **일반 규칙**: "사람은 ~한다", "~하면 누구나 ~하게 된다" 식의 **일반화된 통찰 선언**은 자기 과시로 읽히기 쉽다. 본인이 그 상황에서 실제로 한 생각·예상으로 낮춰 쓴다. 뒤이은 문장(설득 과정 서술)도 극적 서사가 아니라 사실 나열로.

### 교정 3. 마무리 전환구의 AI 냄새

- **스킬 산출물**: *"두 가지가 남았습니다."*
- **사용자가 원한 형태**: *"이 일로 알게 된 것은 두 가지였습니다."*
- **일반 규칙**: "~가 남았습니다", "정리하면 이렇습니다", "결론은 하나입니다" 같은 **문학적 전환구**는 AI 글의 전형이다. 무엇을 통해 무엇을 알게 됐는지 사실 그대로 진술하는 형태로 바꾼다.

### 교정 4. 도입부 — 사실 진술보다 당시 감정을 담기

- **스킬 산출물**: *"사이드 프로젝트에서 팀이 DDD 도입을 제안했습니다. 저도 그 방법론에 끌린 사람 중 하나였습니다."*
- **사용자가 원한 형태**: *"과거 사이드 프로젝트에서 팀이 DDD 도입을 제안했던 일이 있습니다. 저도 그 이름에 매력을 느끼는 사람 중 하나였기 때문에, 거부감 없이 오히려 설레는 마음으로 이를 받아들였습니다."*
- **읽어낼 점**: 시점("과거", "~했던 일이 있습니다")을 분명히 해 회고임을 알리고, 당시 자신의 태도를 **한 겹 더 구체적으로** 적는다("끌렸다" → "거부감 없이 오히려 설레는 마음으로 받아들였다"). 이 정도의 자기 감정 서술은 사용자가 직접 원한 것이므로, 톤 규칙의 "과장된 감정 서술 금지"와 혼동하지 않는다 — 금지 대상은 **AI가 지어낸** 감정이지, 본인이 밝힌 당시 심경이 아니다.

### 이번 건에서 재확인된 것

- 사용자가 "이 정도 표현으로 바꿔달라"며 **직접 대체 문구를 제시**하면, 그 문구를 그대로 쓰되 앞뒤 문장의 격식·리듬만 맞춘다. 더 나은 표현을 제안해도 되지만(사용자가 그렇게 허용한 경우), 기본은 제시된 문구 채택이다.
- 원문에 있다는 사실만으로 링크드인 포스트에 그대로 넣어도 되는 건 아니다. 이미 "블로그 문체에는 맞지만 링크드인엔 자제할 단어" 규칙이 있는데, **문장 단위의 톤(자기 과시, 극적 서사)에도 같은 판단이 필요**하다는 게 이번에 드러났다.

## 2026-08-12 — 같은 소스, 에이전트 초안 vs 사용자 직접 작성본 전면 대조 (가장 중요한 참고 자료)

**상황**: 가족 아카이브 개발기(shnowball.tistory.com/223)로 에이전트가 3버전을 냈으나 사용자가 전부 반려하고 **직접 초안을 작성**했다. 같은 원문에서 출발한 두 결과물을 대조할 수 있는 유일한 사례이므로, 프로젝트 경험형 글을 쓸 때 이 항목을 먼저 읽는다.

### 차이 1. 기술 정보의 위상이 정반대였다 (가장 큰 격차)

| | 에이전트 초안 | 사용자 초안 |
|---|---|---|
| 기술 스택 | Next.js, Cloudflare Workers, R2, Supabase 전부 명시 | **하나도 없음** |
| 성능 수치 | 4.76MB→46KB, JS 730KB→853KB, 800ms, 0.4초, 2~3초 | **없음** |
| 아키텍처 판단 | R2 egress 무료, 바이너리/메타데이터 분리, CI/CD Git 연동, EC2 비교 | **통째로 빠짐** |
| 비용 | 썸네일 3안 비교를 문단으로 전개 | "구현 비용이 낮아지고" 정도의 개념 언급 |
| 서비스워커 | 동작 원리와 스케줄러 분리 이유까지 설명 | "구현과 테스트는 완료했지만 아직 진짜 알림이 간 적은 없다"만 |

**읽어낼 점**: 프로젝트 경험형 글에서 기술 디테일은 본체가 아니다. 상세는 블로그 링크가 맡고, 포스트는 문제와 사람을 다룬다.

### 차이 2. 요청받은 축을 균등 배분하지 않았다

사용자는 "기획/디자인/비용/아키텍처 의사결정/피드백 루프가 드러나게"라고 요청했다. 에이전트는 이를 **체크리스트로 읽고 다섯 축에 지면을 나눠 배정**했다. 그런데 정작 사용자 본인의 글에서는:
- 피드백 루프와 그로 인한 변화가 본체(전체의 절반 이상)
- 기획은 "MVP를 최대한 작게 + 업로드 방식 고민" 두 문단
- 디자인은 "구리다는 피드백 → 앨범 표지 연출" 한 문단
- 비용은 개념으로만 한 번
- 아키텍처는 **아예 없음**

**읽어낼 점**: 요청받은 축은 재료 목록이지 배분표가 아니다. 축을 다 채우려 하면 글이 리포트가 된다.

### 차이 3. 분량이 절반 이하

에이전트 약 3,000자, 사용자 약 1,300자. "원문 충실도" 규칙을 사실상 "빠짐없이 옮기기"로 해석한 결과였다. 원문이 길수록 더 덜어내야 한다는 반대 방향의 감각이 필요하다.

### 차이 4. 문체 — 격식 혼용과 감정 노출

사용자 초안은 "-습니다"가 기본이지만 자연스럽게 섞는다.
- "저는 이 불편함을 발견하지 못했다는 게 또 '만든 사람의 시선은 객관적이지 못하구나' 라고 생각했어요."
- "또 저는 보지 못했던 이런저런 불편이 있겠지요."
- "장문의 카톡피드백을 받았습니다(...)."

에이전트 초안은 전부 "-습니다"로 통일돼 있고 감정 표현이 없어서 리포트처럼 읽힌다. **감정을 드러내는 것과 극적 서사를 지어내는 것은 다르다** — 전자는 권장, 후자는 금지.

### 차이 5. 인용을 한 조각만 살린다

사용자: `"이건 매우 가독성이 떨어지고 디자인이 구리다"로 시작하는 장문의 카톡피드백을 받았습니다.`
실제 워딩은 앞머리만 쓰고 나머지는 "요지는 ~였습니다"로 요약했다. 인용 전체를 재현하려 애쓸 필요가 없다.

### 차이 6. 첫 줄이 훅이 아니다

사용자: "가족들 사이에서 공유되던 문제를 해결하는 사이드 프로젝트를 만들어 봤습니다."
에이전트: "가족 사진이 각자의 폰과 여러 단톡방에 흩어져 있었습니다."

에이전트 쪽이 훅으로는 낫지만, 사용자는 담백한 소개를 택했다. 훅을 짜내는 것보다 자연스러운 진입이 우선일 수 있다.

### 이 사례가 만든 규칙 변경

`SKILL.md` 3단계에 **원문 유형 판별(A. 학습·성찰형 / B. 프로젝트 경험형)** 을 신설하고 유형별 서술 원칙을 분기시켰다. 기존 "원문 충실도" 규칙은 A형 전용으로 스코프를 좁혔다. 함께 반영된 것: 기술 디테일 포함 여부는 매번 질문, 종결어미 혼용 허용, 감정·미완결 노출 허용, 첫 줄 훅 완화.
