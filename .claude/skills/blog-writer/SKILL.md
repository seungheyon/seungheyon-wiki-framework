# blog-writer

스타일 프로필(`blog/concepts/스타일_프로필.md`)과 학습 내용을 바탕으로 블로그 초안을 작성한다.
리뷰어 피드백이 있으면 이를 반영해 재작성한다.

> 이전 버전은 `blog/raw/*.md`를 매번 직접 읽어 문체를 참고했으나, 실제 비교 결과 스타일 프로필 기반 작성이 더 나은 것으로 확인되어 이 방식으로 교체했다(경위는 루트 `log.md` 참고). `blog/raw`는 여전히 프로필의 원재료로 남아있고, 프로필은 [[blog-extract-style]]이 갱신한다.

---

## 언제
- 트리거: [[blog-post]]로부터 호출, 또는 "초안 써줘", "이 내용으로 블로그 글 써줘".

## 실행 흐름

### 1. 사전 확인

`blog/concepts/스타일_프로필.md`가 존재하는지 확인한다.

- **없는 경우**: 다음을 안내하고 중단한다.
  > "스타일 프로필이 없습니다. 먼저 blog-extract-style을 실행해 문체를 학습시켜 주세요." ([[blog-extract-style]])
- **있는 경우**: 파일을 읽고 분석 내용을 내재화한다. 특히 아래 항목을 주의 깊게 숙지한다.
  - A영역: 어투/격식 수준
  - B영역: 종결 어미 형태, 문장 끝 뉘앙스
  - C영역: 한자어 밀도, 한/영 혼용 패턴, 특징적 어휘
  - D영역: 단락 길이, 리스트 vs 산문 판단 기준, 소제목 스타일
  - E영역: 글 시작/마무리 방식, 전환 표현 패턴
  - F영역: 감정/태도 표현 방식
  - 대표 표현 모음: 실제 문체 재현의 핵심 참고 자료

### 2. 동작 모드 판단

**리뷰어 피드백이 함께 전달된 경우** → [6. 재작성 모드]로 이동
**그렇지 않은 경우** → [3. 학습 내용 수집]으로 이동

### 3. 학습 내용 수집 (초안 작성 모드)

사용자가 학습 내용을 함께 제공하지 않았다면 요청한다.

> "어떤 내용을 배웠는지 알려주세요. 정리되지 않은 메모, 개념 요약, 코드 스니펫 등 어떤 형태든 괜찮습니다."

(파일 경로 지원은 아직 없음 — 필요해지면 그때 추가한다.)

학습 내용에 특정 아티클·책·영상 등 외부 출처가 언급되면(예: "~을 읽고", "~아티클을 통해"), 4가지 평가 기준과 별개로 **항상** 원문 링크를 확인한다.

> "참고한 원문 링크가 있으면 알려주세요. 초안에 출처로 남길 수 있습니다."

사용자가 링크를 제공하면 초안 본문에 자연스럽게 포함시킨다(예: "~의 글(링크: ...)을 읽고"). 링크가 없다고 답하면 생략한다.

### 4. 내용 평가 및 Q&A

학습 내용을 아래 4가지 기준으로 평가한다.

| 기준 | 판단 질문 |
|---|---|
| 맥락 | 왜 이걸 배웠는지 배경이나 계기가 있는가? |
| 과정 | 막혔던 부분, 실수, 삽질 흔적이 있는가? |
| 인사이트 | 배우고 나서 관점이나 생각이 달라진 것이 드러나는가? |
| 구체성 | 단순 개념 나열이 아닌 실제 경험이 담겨 있는가? |

**부족한 기준이 있을 경우**, 해당하는 질문만 선별해 **한 번에 최대 3개** 질문한다.
질문 선택 우선순위: **인사이트 > 과정 > 맥락 > 구체성** 순으로 중요도가 높은 항목을 먼저 채운다.

**질문 후보 풀**
1. (인사이트) 한 줄로 요약한다면 핵심 인사이트가 뭐라고 생각하나요?
2. (인사이트) 배우기 전과 후로 생각이나 관점이 달라진 게 있나요?
3. (과정) 배우면서 막혔던 부분이나 처음에 잘못 이해했던 게 있었나요?
4. (맥락) 이걸 배우게 된 계기나 배경이 뭔가요?
5. (구체성) 이 내용이 실제로 어떤 상황에서 도움이 됐나요 (또는 될 것 같나요)?

**운영 규칙**
- 사용자가 "없음", "모르겠음", "패스" 등으로 답하면 해당 항목은 스킵한다.
- 답변을 받은 후 여전히 부족하다고 판단되면 **1회에 한해** 추가 질문할 수 있다.
- 질문에 답하지 않은 항목은 글에 포함하지 않는다. 추론으로 채우지 않는다.

### 5. 초안 작성

#### 문체 재현 원칙
- 스타일 프로필의 **대표 표현 모음**을 few-shot 참고 자료로 활용한다.
- 종결 어미는 프로필에서 관찰된 형태를 그대로 따른다.
- 한자어 밀도, 한/영 혼용 빈도, 특징적 어휘를 프로필 수준에 맞춘다.
- 글 시작과 마무리는 프로필의 내러티브 패턴을 따른다.
- 전환 표현은 프로필에서 발췌된 표현을 우선 사용한다.

#### 내용 구성 원칙
- 사용자가 제공한 내용과 Q&A 답변만을 재료로 쓴다.
- **사용자가 말하지 않은 경험, 시도, 인사이트를 추가하지 않는다.**
- 사용자가 겪은 어려움, 실수, 발견의 순간이 있다면 글의 중심에 놓는다.
- SEO나 포괄적 설명이 목적이 아니다. 이 사람이 이 내용을 배우며 무엇을 느끼고 깨달았는지가 중심이다.
- 사용자가 과거의 오해·실수를 자료로 제공한 경우, 그걸 얼마나 단정적으로 "틀렸다"고 서술할지는 **사용자가 실제로 쓴 표현의 강도**를 따른다. 자료에 "딱히 틀린 건 아니다", "~인 것 같다" 같은 유보적 표현이 있으면 그 유보를 그대로 살리고, 임의로 "내가 틀렸었다"는 단정적 자기반성으로 각색하지 않는다.

#### 주장 세기 검증 (기술 글에서 특히 중요)

블로그는 외부에 공개되는 글이다. 질문 한 번에 무너지는 문장이 하나라도 있으면 글 전체의 신뢰도가 거기까지 내려간다. **문체 재현은 주장의 정확성보다 절대 우선하지 않는다.**

- 단정형·대구·`[대괄호]` 강조 같은 형식은 **주장의 세기를 올리도록 압력을 가한다.** 근거는 "때때로"인데 문장은 "언제나"로 나가기 쉽다. 형식을 맞추느라 세기가 올라가지 않았는지 문장 단위로 확인한다.
- `~수밖에 없다`, `대개`, `본질은 ~이다`, `모든/항상`, `A는 X를 묻고 B는 Y를 묻는다` 류의 대구를 쓰기 전에 **반례를 한 줄 떠올려 본다.** 반례가 붙으면 범위를 좁히거나 유보형(`~것 같다`, `~경우가 늘어난다`)으로 낮춘다.
- 빈도 주장(`대개`, `보통`)은 근거가 없으면 **구체적인 예 하나로 대체한다.** 예가 있으면 빈도를 주장할 필요가 없다.
- 상대 진영·통념을 비판할 때는 **실제 관행을 대상으로 삼는다.** 극단적으로 그린 뒤 때리면 허수아비 지적을 받는다.
- 인접 문단이 방금 쓴 주장을 무력화하지 않는지 확인한다(예: "A만의 강점"이라고 써놓고 다음 문단에서 "B도 그렇게 한다"고 인정하는 것).
- **초안을 제출할 때 사실 / 추론 / 전망을 구분해 표시한다.** 사용자가 "이거 진짜 맞아?"라고 물어야 나오는 게 아니라, 처음부터 붙여서 낸다. 문헌·정의로 뒷받침되는 것만 사실로 표시한다.

#### 금지 패턴 (AI 냄새 원인)

**우선순위 원칙**: 사용자 문체 재현이 금지 패턴 회피보다 항상 우선한다.
스타일 프로필의 대표 표현 모음 또는 각 영역 분석에서 아래 패턴이 사용자의 실제 표현으로 관찰된 경우, 해당 항목은 금지 패턴으로 적용하지 않는다.

아래 패턴은 **프로필에서 관찰되지 않은 경우에만** 사용하지 않는다.

- `또한`, `더불어`, `이를 통해`, `결론적으로`, `중요한 점은`, `주목할 만한 것은` 등 전형적 AI 연결어
- 모든 경우를 빠짐없이 정리한 듯한 완결성 과잉 리스트
- `~할 수 있지만, 반면에 ~하기도 합니다` 류의 지나치게 균형 잡힌 문장 반복
- 강한 의견 없이 항상 중립을 유지하는 서술
- 개론 → 본론 → 결론으로 이어지는 지나치게 교과서적인 구조
- "결론에 이르렀다", "인정할 수밖에 없었다" 등 극적·과장된 감정 서술
- 대시(em-dash "—", 하이픈 "-", "ㅡ" 등)로 부연을 삽입하는 습관 — 프로필/샘플에서 관찰되지 않음. 부연은 괄호로 처리한다.
- **명사구를 쉼표로 나열하고 온점으로 끝맺는 문장.** `A, B, C.` 형태로 서술어 없이 항목만 늘어놓고
  마침표를 찍는 것은 전형적인 AI 문형이다. 예: "테스트 코드의 의미는 3가지가 있다. 검증 자체, 안정감 확보,
  결합도 낮은 코드." 한국어 구어/서술문에서는 이렇게 끊지 않는다 — 서술어를 붙여 완결된 문장으로 쓰거나
  (`검증 그 자체이고, 안정감을 확보해주며, 결합도가 낮은 코드를 만들게 한다.`), 항목마다 설명이 필요하면
  문장을 나눠 각각 서술한다. 개수를 예고하는 도입(`~는 3가지가 있다`)과 짝을 이룰 때 특히 냄새가 강해진다.
- **강조가 필요 없는 대목에 소제목·볼드 라벨을 붙여 극적 서사를 만드는 것.** 사건을 나열할 때마다
  `**소제목.**` 형태로 라벨을 달거나, 성격이 비슷한 항목들을 굳이 상위/하위 주제로 갈라 구조를
  만드는 것은 AI 작문의 대표적 흔적이다. 실제로 강조가 필요한 곳(글의 주장이 걸린 지점, 반전이
  일어나는 지점)에서만 강조하고, 나머지는 평범한 산문으로 이어 쓴다. 특히 **분류 자체가 글의
  논지가 아닌데 분류 구조를 만드는 것**을 경계한다 — 예: 개선 사항을 "내가 찾은 것 / 남이 알려준
  것"으로 섹션을 갈라 놓는 식. 출처를 정확히 쓰는 것과, 그 구분을 글의 뼈대로 삼는 것은 다르다.

#### 분량 가이드
재료에 명시적으로 등장하는 문제, 해결 시도, 인사이트 각 항목은 나열로 압축하지 않는다. 각 항목이 왜 발생했는지, 어떤 상황에서 등장했는지를 포함해 실질적인 분량으로 서술한다.
분량은 재료를 따른다. 재료가 풍부하다면 글도 충분히 길어져야 하며, 분량을 줄이거나 내용을 압축하려는 경향을 억제한다.

#### 구조 가이드
블로그 글에 반드시 포함해야 할 구성 요소는 없다. 단, 자연스러운 흐름이 있어야 한다.
아래는 참고용 흐름이며, 프로필의 내러티브 패턴에 따라 자유롭게 변형한다.

```
왜 이걸 배웠는가 (또는 어떤 상황에서 마주쳤는가)
  ↓
배우면서 겪은 것 (막힌 것, 헷갈린 것, 시도한 것)
  ↓
이해하게 된 것 (인사이트, 관점 변화)
  ↓
(선택) 앞으로 어떻게 쓸 것인가 / 남은 궁금증
```

#### 소제목·도입부 원칙 (발행본 대조로 확인된 것 — 2026-08-19)

writer 초안을 사용자가 직접 손봐 발행한 글을 대조해 나온 규칙이다. 근거와 대조표는
`blog/concepts/스타일_프로필.md` "편집 대조 관찰" 절에 있다. **아래는 문체 재현 항목이므로
금지 패턴보다 우선한다.**

- **소제목은 명사 라벨로 쓴다.** 그 절의 주제를 지목하는 이름이지, 절에서 일어난 일을 서술하는
  문장이 아니다. `그래도 수량이 맞지 않았다` → `중복 발급 문제`, `같은 버그인데 크기가 달랐다` →
  `인메모리 DB가 가렸던 문제`. 반전을 예고하거나 긴장을 만드는 제목을 쓰지 않고, **원인·주제를
  앞에 내놓는다.**
- **같은 층위의 소제목은 한 축으로 통일한다.** `JVM 락 / DB 락 / redis 락(Lettuce) /
  redis 락(Redisson)` 처럼 형태를 맞춘다. 내용상 성격이 달라도(교체·개선) 계열 명칭을 우선한다.
- **도입부에서 붙인 명칭이 그대로 소제목이 되게 한다.** 도입부의 나열도 동사구가 아니라
  명사 라벨로 쓴다(`자바 어플리케이션 락, DB 락, 외부 저장소(redis 등) 락`).
- **소제목에서 담화 접속어를 뗀다.** `그런데 서버가 한 대가 아니라면?` → `서버가 한 대가 아니라면?`.
  반문형 소제목 자체는 사용자 습관이므로 유지한다.
- **일반 분류어보다 겪은 것을 가리키는 말을 쓴다.** `단점` → `문제`.
- **글 제목은 반문형이 아니라 범위 안내형으로, 괄호에 다루는 항목을 열거한다.**
  `쿠폰 발급 프로젝트와 동시성 제어(JVM 락, DB 락, Redis 락)`. 반문은 소제목에서만 쓴다.
- **도입부에서 글의 구조를 설명하지 않는다.** `환경을 먼저 적어 둔다`, `이 차이가 나중에 큰 이야기가
  된다`, `하나는 ~이고 다른 하나는 ~이다` 같은 안내·예고·목차 문장은 전부 제거 대상이다. 예고하고
  싶은 자리에는 **그 시점에 자기가 무엇을 느꼈는지**를 쓴다(`영영 모르고 지나갈 뻔 했다`).
- **개요에서 본문 내용을 미리 풀지 않는다.** 무엇을 다루는지만 밝히고 결론·경위는 본문에 맡긴다.
- **대괄호 강조는 개념·단위에 이름을 붙일 때만 쓴다.** 평범한 서술구를 강조하려고 씌우지 않는다.
- **개요의 마무리 문장은 격식 과거형으로 맺는다** — `~을 담았다`, `~을 첨부하였다`.

#### 단락 구성 원칙
맥락상 이어지는 내용이고 단락을 분리할 필요가 없으면 굳이 분리하지 않는다. 과하게 많은 단락이나 짧은 단락은 읽는 경험의 질을 크게 떨어뜨린다.

### 6. 재작성 모드

리뷰어 피드백을 수신한 경우 아래 순서로 처리한다.

1. 피드백에서 **하드 블로커 실패 항목**을 먼저 확인한다. 해당 항목을 최우선으로 수정한다.
2. **점수 미달 항목**별 피드백을 읽고, 각 지적 사항에 대응하는 수정을 한다.
3. 피드백에 명시되지 않은 부분은 원문을 유지한다. 과도한 수정으로 통과된 항목을 훼손하지 않는다. 단, 피드백에 **'전면 재서술 필요'**가 명시된 섹션은 원문 유지 제약을 해제하고, 해당 섹션을 충분히 펼쳐 재서술한다.
4. 수정 후에도 5단계의 문체 재현 원칙과 금지 패턴 규칙을 동일하게 적용한다.

### 7. 출력

작성된 초안을 마크다운 형식으로 출력한다.
[[blog-post]]에 의해 호출된 경우 출력값을 그대로 반환한다(저장은 blog-post가 최종 단계에서 처리).

직접 호출된 경우, 저장 전에 파일명에 제목을 반영할지 먼저 묻는다.

> "초안 파일명에 제목을 반영할까요? 반영한다면 어떤 제목으로 할까요? (원치 않으면 기존처럼 날짜만 사용합니다)"

- **제목을 받은 경우**: `blog/drafts/YYYY-MM-DD_<제목>.md`로 저장한다. 제목의 공백은 밑줄(`_`)로 바꾸고, 파일명에 쓸 수 없는 특수문자(`? : \ / * < > | "`)는 제거한다.
- **원치 않는다고 답한 경우**: 기존대로 `blog/drafts/YYYY-MM-DD_draft.md`로 저장한다.
- 같은 날짜·같은 이름으로 이미 파일이 있으면 `_2`, `_3`... 넘버링한다.

저장 후 초안을 출력하고 다음을 안내한다.

> "초안이 작성됐습니다. blog-post를 실행하면 리뷰 및 최종 검토 단계로 넘어갑니다."
