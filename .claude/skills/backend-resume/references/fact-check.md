# 이력서 사실 검증 체크리스트

이력서는 면접에서 한 줄씩 캐물리는 문서다. **사용자가 준 피드백이라도 그대로 반영하지 않는다.**
아래를 통과하지 못한 항목은 반영 전에 지적하고 확정을 받는다.

---

## A. 수치 정합성

- [ ] as-is / to-be 값과 **개선율의 산수가 맞는가**
      (예: 350ms → 80ms는 약 77% 개선이지 70%가 아니다)
- [ ] 같은 수치가 위키·raw의 다른 곳과 어긋나지 않는가. 어긋나면 어느 쪽이 맞는지 확정받는다
- [ ] 측정 조건(예열 여부, 커넥션 재사용, 캐시 적재, 동시 요청 수)이 before/after 동일한가
- [ ] 조건이 다르면 수치를 나란히 놓지 않고 조건을 명시한다

## B. 경험 실재성

- [ ] 이 문장에 쓰인 기술·활동이 위키 또는 raw에 근거가 있는가
- [ ] 근거가 없으면 **사용자에게 확인**한다. "그럴듯하니 넣는다"는 없다
- [ ] 사용자가 새로 말한 경험이라도, 기존 기록과 충돌하면 어느 쪽이 맞는지 확정받는다
- [ ] 계획만 하고 안 한 것을 한 것처럼 쓰지 않는다

## C. 화자·출처 구분

- [ ] "타인의 피드백"과 "본인이 직접 발견한 것"을 섞지 않았는가
      (유저 피드백 축에 본인 QA 결과를 넣는 실수가 실제로 있었다)
- [ ] 팀 프로젝트에서 **본인이 담당한 범위**만 성과로 쓰고 있는가

## D. 제약 서술

- [ ] "~때문에 불가능했다"는 서술이 정말 불가능이었는가
- [ ] 자동화 경로 하나가 막힌 것을 작업 자체의 불가능으로 확대하지 않았는가
- [ ] 뻔한 대안(대시보드, 수동 실행 등)이 시도된 기록이 있는가.
      없으면 "이 경로가 막혔다"로 범위를 좁혀 쓴다

## E. 용어 충돌

- [ ] 프로젝트명·고유명사가 위키의 다른 개념과 이름이 겹치지 않는가
- [ ] 겹치면 이력서 안에서 둘을 구분할 수 있는 표현을 쓰고 있는가

## F. 링크·자산

- [ ] 외부 링크(블로그 등)가 실제로 그 내용을 담고 있는가 (열어서 확인)
- [ ] 이미지 상대경로(`assets/...`)가 PDF 변환 시에도 유효한가

---

## 검증 실패 시 행동

1. 어떤 항목이 왜 어긋나는지 **근거(파일·수치)와 함께** 사용자에게 알린다
2. 선택지를 만들어 AskUserQuestion으로 확정받는다
3. 확정된 내용이 기존 위키와 다르면, 이력서와 위키를 **함께** 고친다
   (raw는 불변 — 위키에 "정정" 사실을 명시한다)
