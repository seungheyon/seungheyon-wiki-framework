# 이력서 문체·구조 규칙

이력서 v1~v7을 거치며 사용자가 직접 반려한 항목들에서 도출된 규칙이다.
새 규칙이 생기면 여기에 append 한다.

---

## 1. 대원칙 — "무슨 문제 때문에 이 기술을 썼는가"

기능을 구현했다·기술을 사용했다 수준의 서술은 쓰지 않는다.
어필 대상이 되는 항목은 반드시 아래 세 조각이 보이게 쓴다.

```
어떤 문제가 있었나  →  왜 이 방법을 골랐나(다른 선택지는 왜 아니었나)  →  결과가 어떻게 달라졌나
```

- 결과는 가능하면 수치로 쓴다. 수치가 없으면 "정량 미측정"임이 드러나는 표현을 쓰되 과장하지 않는다.
- 실패한 1차 시도가 있으면 넣는다. 시행착오는 감점이 아니라 사고 과정의 증거다.
- 다만 실패 서술이 길어지면 안 된다. "무엇을 시도했고 왜 안 됐는지" 한 줄이면 충분하다.

---

## 2. 금지 패턴 (AI 티가 나는 서술)

사용자가 실제로 반려한 항목들이다. 예외 없이 적용한다.

| 금지 | 이유 / 대체 |
|---|---|
| **em대시(—)** | "AI가 썼습니다" 하고 소문내는 꼴. 부연은 괄호로 처리하거나 문장을 나눈다. 작성 후 전체 재검색해 잔여분을 제거한다 |
| **산문형 긴 문단** | 이력서는 불릿 문서다. 3줄 넘는 설명 문단은 불릿로 쪼갠다 |
| 볼드 남용 | 볼드는 **핵심 성과·수치**에만. "시행착오:", "실측:" 같은 라벨에는 쓰지 않는다 |
| 하이라이트 남용 | 형광 하이라이트는 페이지당 소수로. 문제 진술의 결론 등 진짜 한 곳에만 |
| 과장된 인과 서술 | "~하여 ~로 이어졌고 결국 ~했다" 류. 사실만 남기고 해석은 뺀다 |
| 근거 없는 제약 서술 | "~때문에 불가능했다"는 표현은 정말 불가능했는지 확인 후에만. 대개는 "특정 경로가 막혔다"가 정확하다 |
| **명사구 나열 + 온점 마무리** | 한 불릿/문장 안에서 `A, B, C.`처럼 서술어 없이 항목만 늘어놓고 마침표를 찍는 문형(예: "테스트 코드의 의미는 3가지. 검증 자체, 안정감 확보, 결합도 낮은 코드."). 전형적 AI 문형이다. 항목이 여럿이면 **각각 별도 불릿으로 쪼개고**, 한 문장 안에 두어야 하면 서술어를 붙여 완결한다. (불릿 자체가 명사형으로 끝나는 건 이력서 관례이므로 해당 없음 — 대상은 한 문장 안의 쉼표 나열) |
| 같은 라벨 반복 | 섹션 제목이 이미 말하는 것을 불릿마다 라벨로 되풀이하지 않는다 |
| 소제목의 음슴체(`~함`, `~됨`) | 헤드라인 불릿의 `.lead` 문구가 "~나눔", "~됨"처럼 명사형 종결로 끝나면 딱딱하고 보고서 티가 난다. 명사형 서술어(분할/일원화/재확인/구성/제한/해결/규명/추적)로 정제한다. 실제 수정: "지식이 쌓이도록 3계층으로 구조를 나눔" → "지식이 쌓이도록 3계층 구조로 분할"(2026-08-09) |

## 3. 가독성 구조 규칙

각 프로젝트 본문은 평평한 불릿 나열이 아니라 **계층**을 갖는다.

```
프로젝트 제목 · 기간 · 유형 · 한 줄 소개 · 역할
  [문제]        문제 진술 1~2줄 + 결론 한 줄
  [축 제목]     ① 제품 기획 / ② 엔지니어링 / ③ 유저 피드백 등
    ▸ 헤드라인 불릿 (볼드, 성과·수치 또는 해결한 문제)
        · 하위 불릿 (실측 / 원인 / 해결 / 검증)
```

- 헤드라인 불릿만 읽어도 "무슨 문제를 어떻게 해결했는지"가 파악돼야 한다.
- 하위 불릿은 헤드라인의 근거다. 헤드라인 없이 하위 불릿만 나열하지 않는다.
- 축(①②③)은 프로젝트마다 성격에 맞게 정한다. 모든 프로젝트에 같은 축을 강제하지 않는다.
- 축이 하나뿐인 프로젝트는 축 제목 없이 헤드라인 불릿만 쓴다.

## 4. 용어·표현

- **영어 프로젝트명 금지**: 한국어 이름을 쓴다. 단 이미 고유명사로 굳은 제품명(MVPQuest, Coupong)은 예외.
- **비개발 독자 배려**: 엔지니어링 축은 채용 담당자가 읽을 수 있는 말로 쓴다.
  전문 용어를 없애라는 뜻이 아니라, 용어를 쓰되 그 옆에 무슨 뜻인지가 드러나게 쓴다.
  - 나쁜 예: "Spring AI RAG Advisor 추상화로 계측 불가"
  - 좋은 예: "RAG 처리가 프레임워크 내부에 감춰져 있어 모델에 실제로 전달되는 프롬프트를 볼 수 없었음"
- **자소서용 순화 정책과 구분**: 자소서에서는 "Zipkin" 대신 "분산 추적 도구"를 쓰지만,
  이력서(개발 직군 리뷰어가 봄)에서는 고유명사를 그대로 쓴다.

## 5. 마크다운·렌더링 주의

- 한 줄에 물결표(`~`)가 두 개 이상 오면 취소선으로 렌더링될 수 있다.
  범위 표기가 겹치면 하나를 "1.4초에서 3.9초"처럼 풀어쓴다.
- 특수문자(`~ * _ #`)가 든 문장을 편집한 뒤에는 원문이 아니라 **렌더링 결과** 기준으로 점검한다.

## 6. 톤 — 겸손하고 인간미 있게 (2026-08-09 추가, 강한 강제)

v8 자기소개에 대한 반려: *"너무 딱딱하고 자신감이 넘친다. 겸손함이 없어 보이고 AI가 쓴 티가 난다."*
경어체(`~습니다`)는 유지하되 아래를 지킨다. **낮추는 것은 단정의 강도이지 성과나 수치가 아니다.**

| 고쳐야 할 것 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 단정 → 경험 | "무엇이 불편한지 정확히 알고 있었기에 서비스로 만들었습니다" | "직접 겪어 불편했던 것들은 계속 붙잡고 있게 됐습니다" |
| 선언 → 지향 | "수치로 확인되지 않은 것은 개선이라 부르지 않습니다" | "원인까지 맡기지는 않으려 합니다" |
| 과장 어휘 | 근본 해결 / 전면 재설계 / 원인을 특정 / 완벽히 | 원인을 다시 찾음 / 다시 설계 / 원인을 찾음 |
| 성과 단정 | "5가지를 한 번에 해결했습니다" | (사실이면 유지) 실제 범위를 넘지 않는지만 확인 |

- **자기 한계를 인정하는 문장을 축마다 하나씩** 둔다. 예: "만든 사람은 자기 제품의 불편을 잘 보지 못한다는
  것을 그때 배웠습니다." 이런 문장이 없으면 전체가 자기 자랑으로 읽힌다.
- 다만 구어체(`~더라고요`, `~같아요`)로 흘러가지 않는다. 겸손과 캐주얼은 다르다.
- 프로젝트 서술도 같은 기준을 적용한다. 사실·수치는 그대로 두고 동사와 수식어만 실제 범위로 좁힌다.

## 7. 자기소개 섹션

- 3개 축, 각 축은 "굵은 한 줄 주장 + 그 근거가 되는 실제 사례 2~3줄" 형태.
- 근거는 반드시 이력서 안의 프로젝트에서 가져온다. 프로젝트에 없는 주장은 쓰지 않는다.
- **첫 축에서 "기술 자체에 매몰되지 않고 실제 문제 해결을 좋아하는 사람"이라는 인상이 나와야 한다**
  (2026-08-09 사용자 요청). 단, 학습 의지가 없어 보이지 않게 균형을 잡는다.
- **비교 구문("A보다 B") 대신 병렬 구문("A도 좋지만 B에 더")을 쓴다.** "A보다"는 A를 깎아내리는
  뉘앙스가 남는다. 실제 반려 사례: "기술을 배우는 것보다 눈앞의 불편이 사라지는 쪽이 더 재미있었습니다"
  → "기술을 배우는 것도 즐겁지만, 눈앞의 불편을 없애는 일이 더 가치있게 느껴집니다"(2026-08-09, 문장 재정제).
- 헤드라인과 본문이 같은 말을 반복하지 않는지 확인한다. 위 사례에서 본문이 이미 "익히는 일도 즐겁지만"으로
  시작하고 있어 헤드라인과 중복이면서 동시에 뉘앙스가 어긋나 있었다.
- AI 활용을 말할 때는 **기본기 경시로 읽히지 않게** 프레이밍한다.
  "코드/프레임워크보다 본질"이 아니라 "AI로 구현 속도를 확보하고, 그 시간을 제품 판단에 쓴다"로 쓴다.
  신입 전형에서 기본기 의심을 부르는 표현은 그 자체로 손해다.

## 8. 개정 시 지켜야 할 것

- 지시받은 항목만 고치되, **문체·디자인 기준은 지시 없이도 유지**한다.
- 이전 버전에서 사용자가 명시적으로 지운 요소(특정 색 바, 특정 문구)를 되살리지 않는다.
- 한 항목을 고치면 그와 연동된 항목(수치와 개선율, 제목과 본문 용어)이 같이 맞는지 확인한다.
